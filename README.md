# Сервис потоковой аналитики рынка Perpetual Futures

> Сбор рыночных событий из Hyperliquid, доставка через брокер сообщений, расчёт минутных агрегатов и мониторинг свежести данных.
>
> **Важно:** проект предназначен для аналитики и демонстрации. Он не является торговой системой, не выдаёт инвестиционных рекомендаций.

## Цель проекта

Построить небольшой сервис, который принимает поток событий perpetual-рынка, сохраняет исходные данные, вычисляет минутные метрики и показывает как рыночные показатели, так и состояние самого data pipeline.

Проект демонстрирует:

- потоковый ingestion через WebSocket;
- публикацию событий в Kafka-совместимый брокер;
- нормализацию и версионирование схемы;
- event-time оконные агрегаты;
- дедупликацию и обработку событий не по порядку;
- восстановление соединения и обнаружение пробелов;
- контроль свежести, задержки и качества данных
- 

## Пользовательский сценарий

Пользователь выбирает perpetual-актив и видит:

- последнюю обработанную цену;
- минутные OHLCV-агрегаты;
- число сделок и объём за минуту;
- изменение цены за минуту;
- время события и задержку его получения;
- статус источника и возраст последнего события;
- признак полноты агрегата и обнаруженные разрывы.

Интерфейс должен явно различать актуальные, устаревшие и неполные данные. Успешный ответ API сам по себе не означает, что поток свежий.

## Объём MVP

Первая версия ограничена следующими рамками:

- один источник рыночных данных — Hyperliquid;
- подписка на поток сделок для небольшого списка активов;
- конфигурируемый список рынков;
- Kafka;
- архив сырых событий локально;
- минутные агрегаты по event time;
- API для чтения агрегатов и состояния ingestion;
- метрики и дашборд технического состояния.

MVP не размещает ордера, не рассчитывает торговые рекомендации и не обещает без потерь восстановить события, если источник не предоставляет подходящую историю.

## Архитектура

```text
Hyperliquid WebSocket
        │
        ▼
Ingestion service ───────────────► Kafka 
                                         │
                                         ├──► Raw archive
                                         │
                                         └──► Stream processor
                                                       │
                                                       ├──► Minute aggregates
                                                       └──► Data-quality state
                                                                │
                                                                ▼
                                                        ClickHouse
                                                                │
                                                                ▼
                                                           Dashboard
```

### Компоненты

1. **Ingestion service** — подключается к WebSocket, управляет подписками, reconnection, heartbeat.
2. **Kafka** — буфер между приёмом и обработкой событий.
3. **Raw archive** — сохраняет исходные payload и метаданные для аудита и повторного расчёта.
4. **Stream processor** — валидирует события, удаляет дубли и считает event-time агрегаты.
5. **Аналитическое хранилище** — хранит готовые минутные агрегаты и состояние качества.
6. **Мониторинг** — экспортирует технические метрики и журналы.

Для локального MVP компоненты могут запускаться одним Docker Compose. Это не предполагает высокой доступности или production-масштаба.

## Поток данных

1. Collector открывает WebSocket-соединение и подписывается на выбранные рынки.
2. Входящее сообщение сохраняется в исходном виде либо вместе с нормализованным событием.
3. Collector добавляет время получения (`received_at`) и технические метаданные.
4. Событие публикуется в брокер с ключом партиционирования, например `asset`.
5. Stream processor проверяет схему, типы и обязательные поля.
6. События дедуплицируются и распределяются по минутным окнам по `event_time`.
7. Агрегаты записываются в хранилище.
8. Метрики pipeline обновляются независимо от рыночных метрик.

## Модель событий

Ниже — внутренняя схема проекта, а не дословный формат сообщения Hyperliquid. Фактический формат подписки `trades` зафиксирован в `tests/fixtures/hyperliquid_trades_btc.json` (одна mainnet-сделка; адреса участников в `users` обезличены). Capture сделан 2026-10-11 UTC с `wss://api.hyperliquid.xyz/ws` после подписки на BTC.

Envelope имеет вид `{"channel":"trades","data":[...]}`. Каждая запись содержит `coin` (символ), `side` (`B` — агрессор-покупатель, `A` — агрессор-продавец), `px` и `sz` (десятичные строки), `time` (Unix timestamp в миллисекундах), `hash` (хэш L1 транзакции), `tid` (50-битный хэш пары order ID) и `users` (адреса покупателя и продавца). Для дедупликации используйте составной ключ `(time, coin, tid)`, а не `tid` отдельно.

| Внутреннее поле | Поле Hyperliquid | Примечание |
|---|---|---|
| `asset` | `coin` | Символ рынка |
| `event_time` | `time` | Timestamp источника, миллисекунды Unix |
| `price` | `px` | Сохранять строкой/Decimal |
| `size` | `sz` | Сохранять строкой/Decimal |
| `side` | `side` | В источнике код `B` или `A`, не `buy`/`sell` |
| `source_event_id` | `time`, `coin`, `tid` | Составной ключ |
| `received_at` | — | Добавляется коллектором; в source payload отсутствует |

Пример в fixture сохраняет одну фактически полученную сделку; два адреса `users` заменены тестовыми адресами, остальные значения и структура взяты из наблюдённого сообщения.

Внутренняя схема события (значения-пример; сырой источник см. в fixture):

```json
{
  "schema_version": 1,
  "source": "hyperliquid",
  "channel": "trades",
  "asset": "BTC",
  "event_time": "2026-10-11T10:53:04.489Z",
  "received_at": "2026-10-11T10:53:41.154Z",
  "price": "82943.0",
  "size": "0.00037",
  "side": "sell",
  "source_event_id": "1791715984489:BTC:306718709943332",
  "connection_id": "collector-session-id",
  "raw_payload": {"coin":"BTC","side":"A","px":"82943.0","sz":"0.00037","time":1791715984489,"hash":"0xde380019a8a5f68adfb1044652332f01c70017ff43a9155c8200ab6c67a9d075","tid":306718709943332,"users":["<redacted>","<redacted>"]}
}
```

Значение `side: "sell"` во внутреннем примере — перевод кода источника `A` (агрессор-продавец); исходный код следует сохранять в `raw_payload`.

### Правила модели

- `event_time` — временная отметка источника, используемая для окон.
- `received_at` — время приёма сервисом, используемое для расчёта задержки.
- Цены и объёмы следует обрабатывать с подходящей десятичной точностью; не применять `float` без осознанного обоснования.
- Если источник предоставляет стабильный идентификатор события, использовать его для дедупликации.
- Сырые payload и нормализованная схема должны быть доступны для диагностики.
- Изменения схемы оформляются новой версией и покрываются тестами.

## Минутные агрегаты

Для каждого актива и минуты рассчитываются:

| Поле | Описание |
|---|---|
| `window_start` | Начало минутного окна в UTC |
| `open_price` | Цена первой сделки по event time |
| `high_price` | Максимальная цена окна |
| `low_price` | Минимальная цена окна |
| `close_price` | Цена последней сделки по event time |
| `trade_count` | Число уникальных сделок |
| `base_volume` | Сумма объёмов в базовом активе |
| `quote_volume` | Сумма `price × size`, если семантика полей источника это допускает |
| `price_change_pct` | Изменение между open и close |
| `last_event_time` | Время последнего учтённого события |
| `max_ingestion_lag_ms` | Максимальная задержка получения события в окне |
| `is_complete` | Признак полноты окна по правилам проекта |

Агрегаты строятся по `event_time`. Поздние события могут изменить уже опубликованное окно. Для этого задаётся grace period; в его пределах агрегат пересчитывается. События, опоздавшие сильнее, сохраняются в raw archive и учитываются в метрике поздних событий. Правило финализации окна должно быть явно задокументировано.

### Дубли и порядок событий

- Повторная доставка одного события не должна удваивать объём или `trade_count`.
- Для дедупликации используется стабильный ID источника, если он доступен.
- События не по порядку обрабатываются по `event_time` в пределах grace period.
- Повторное построение агрегатов выполняется из raw events, а не из уже агрегированных строк.

### Rate limits

- Повторные подключения и запросы не должны создавать шторм обращений.
- Следует соблюдать ограничения числа соединений, подписок и запросов источника.
- Ошибки ограничения частоты должны быть видны в логах и метриках.
- Реальный набор лимитов и доступных методов сверяется с актуальной документацией API.

## Тестирование

### Unit-тесты

- нормализация сообщений источника;
- обработка decimal-полей и timestamp;
- расчёт OHLCV;
- дедупликация;
- обработка позднего события;
- финализация окна и признак полноты.

### Integration-тесты

- публикация и чтение события через брокер;
- запись агрегата в хранилище;
- проверка API-контракта;
- повторное получение события без двойного учёта.

### Сценарии отказа

- принудительный разрыв WebSocket;
- недоступность брокера;
- перезапуск consumer;
- некорректное сообщение;
- повторная доставка;
- событие вне порядка;
- недоступность endpoint истории;
- превышение rate limit.

Для детерминированных тестов используйте сохранённые fixtures или синтетические события. Не делайте unit-тесты зависимыми от доступности внешнего API.

## План разработки

### Этап 1. Исследование источника

- выбрать канал событий и несколько perpetual-рынков;
- сохранить реальные примеры сообщений;
- проверить поля времени, цены, размера и идентификаторов;
- выяснить доступность истории для backfill;
- задокументировать ограничения API и rate limits.

### Этап 2. Collector

- реализовать соединение и подписки;
- добавить heartbeat, reconnect и ограничение частоты повторных попыток;
- валидировать и публиковать события;
- покрыть логику тестами.

### Этап 3. Обработка и агрегаты

- настроить consumer;
- реализовать event-time окна, дедупликацию и grace period;
- сохранять агрегаты и полноту окон;
- добавить тесты на повторы и события не по порядку.

### Этап 4. Восстановление

- принудительно симулировать обрыв;
- проверить повторное подключение и восстановление подписок;
- реализовать backfill, только если он поддерживается источником;
- отображать невосстановленные интервалы как gaps.

### Этап 5. API и интерфейс

- опубликовать агрегаты и состояние данных;
- добавить визуальные статусы свежести и полноты;
- подготовить примеры запросов и скриншоты.

### Этап 6. Эксплуатационная готовность

- настроить метрики, логи и health checks;
- добавить CI и запуск локального окружения;
- описать известные ограничения, архитектурные решения и runbook.

## Ограничения и допущения

- Поля и семантика сообщений должны быть подтверждены по фактическому payload выбранного канала.
- Backfill не считается гарантированным, пока не проверена доступность истории именно для выбранного типа событий.
- Данные внешнего источника могут задерживаться, повторяться или быть временно недоступными.
- Минутная агрегация и признак полноты определяются правилами проекта; это не официальные показатели биржи.
- Результаты зависят от локальной доступности API, брокера, сети и выбранных лимитов.
- До публикации проекта нужно проверить условия использования источника и корректно указать его атрибуцию, если она требуется.
